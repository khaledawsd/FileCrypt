How verification works

  • A key file carries a SHA-256 of the original bytes. After decrypting, the result is hashed and compared.
  • A passphrase file carries a MAC instead, checked before decrypting, so a wrong passphrase costs you nothing but the attempt.
  • Either way a mismatch is reported: you never get handed a corrupt file silently, and the page tells you which check ran.

Authenticated by default

AES-256-GCM detects a wrong key or a modified file instead of returning garbage.

Nothing is stored

No database, no upload folder, no accounts. The request is handled in memory and forgotten.

Security

What this does and does not protect

Worth reading before you trust it with anything real.

AES never leaves the tab

AES-256-GCM is encrypted by your browser through the Web Crypto API. No request is made at all, so you can watch the network tab stay empty.

The rest run on this machine

The other seven go to the Python process you started, on this computer. It holds the plaintext in memory while it works. Nothing travels over a network unless you deliberately expose it to one.

Nothing is stored, anywhere

No database, no upload directory, no session, no log. Once a result is handed back there is no copy of your file or your key left.

Lose the key file and the data is gone. There is no recovery, no reset, and no copy. That is the direct consequence of storing nothing.
This is built to be cloned and run locally, not deployed. It uses Flask's development server and has no authentication or rate limiting, so don't put it on a public address as-is.
FAQ

Questions worth asking

Is my file really encrypted in the browser?

For AES-256-GCM, yes. It is encrypted in the tab with the Web Crypto API and no request is made. The result panel says so, and the network tab will show nothing to look at.

For the other seven, no. Web Crypto has no Blowfish and no Fernet, and writing the three educational algorithms a second time in JavaScript would mean two implementations of an unreviewed cipher that could quietly disagree about what a file holds. Those go to the Python process on your machine, which sees the plaintext while it works. The page tells you which path ran, every time.

What happens if I lose the key file?

The file stays encrypted forever. No account holds a backup, because there are no accounts. Keep the .key.json somewhere you trust. A password manager works well.

Which algorithm should I pick?

AES-256-GCM unless you have a specific reason otherwise. It is authenticated, fast, and handles any file type. Fernet and the hybrid RSA option are also solid choices.

Why does visual cryptography behave differently?

Because it is not a file cipher. It splits an image into two share images; either one alone is noise, and stacking them reveals the picture. You get a zip of both shares instead of an encrypted file.

Stacking returns a black-and-white approximation at double the original size, not your original bytes. Print the shares on transparencies and overlay them; it works with no computer at all.

How does it know my key is wrong?

The key file stores a SHA-256 of the original file. After decryption the result is hashed and compared. AES, Fernet and RSA would catch a bad key on their own; the demo algorithms are raw transforms that would otherwise hand back plausible-looking garbage.

Is there a file size limit?

{{ max_mb }} MB by default, because a request briefly holds the file, its ciphertext, and the encoded response in memory at once. Raise it with the MAX_UPLOAD_MB environment variable.

How verification works

  • The key file carries a SHA-256 of the original bytes.
  • After decrypting, the result is hashed and compared.
  • A mismatch is reported as a wrong key — you never get handed a corrupt file silently.

Security

What this does and does not protect

Worth reading before you trust it with anything real.

Encryption runs on the server

Your file is uploaded, encrypted in memory, and the response is sent. Nothing is written to disk. But the server does see your plaintext while it works — this is not end-to-end encryption.

No retention of any kind

There is no database, no upload directory, and no session. Once the response is sent there is no copy of your file or your key anywhere on the server.

Deploy it properly

Ships with Flask's development server and no rate limiting. Put it behind HTTPS and a real WSGI server before exposing it to a network.

Lose the key file and the data is gone. There is no recovery, no reset, and no copy. That is the direct consequence of storing nothing.
FAQ

Questions worth asking

Is my file really encrypted in the browser?

No, and it is worth being clear about that. The file is uploaded and encrypted on the server, then the result comes back to you. Nothing is stored, but a compromised server could read the file while it is being processed.

If you need the server never to see your plaintext, the crypto has to run in the browser via the Web Crypto API. That is a different design.

What happens if I lose the key file?

The file stays encrypted forever. No account holds a backup, because there are no accounts. Keep the .key.json somewhere you trust — a password manager works well.

Which algorithm should I pick?

AES-256-GCM unless you have a specific reason otherwise. It is authenticated, fast, and handles any file type. Fernet and the hybrid RSA option are also solid choices.

Why does visual cryptography behave differently?

Because it is not a file cipher. It splits an image into two share images; either one alone is noise, and stacking them reveals the picture. You get a zip of both shares instead of an encrypted file.

Stacking returns a black-and-white approximation at double the original size, not your original bytes. Print the shares on transparencies and overlay them — it works with no computer at all.

How does it know my key is wrong?

The key file stores a SHA-256 of the original file. After decryption the result is hashed and compared. AES, Fernet and RSA would catch a bad key on their own; the demo algorithms are raw transforms that would otherwise hand back plausible-looking garbage.

Is there a file size limit?

{{ max_mb }} MB by default, because a request briefly holds the file, its ciphertext, and the encoded response in memory at once. Raise it with the MAX_UPLOAD_MB environment variable.
